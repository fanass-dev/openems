= EVCS go-e Gemini Managed (JSON API v2)

Nicht Teil des offiziellen OpenEMS-Projekts (custom Bundle dieser Installation).

== Zweck

Steuert einen go-e Gemini Ladepunkt aktiv (PV-Überschussladen via
`Controller.Evcs`) über die öffentlich dokumentierte, aber inoffizielle
go-e-API-v2 (https://github.com/goecharger/go-eCharger-API-v2, Endpunkte
`/api/status` und `/api/set`).

== Warum ein separates Bundle statt das bestehende `Evcs.Goe.Http` zu erweitern

Das mitgelieferte `io.openems.edge.evcs.goe`-Bundle ("Evcs.Goe.Http"/
"Evcs.Goe.Modbus") implementiert für die Gemini-Baureihe **kein**
`ManagedEvcs` - auch nicht, wenn dessen `readOnly`-Config-Feld auf `false`
gesetzt wird (dieses Feld beeinflusst nur den gemeldeten `MeterType`, keine
tatsächliche Schreibfähigkeit). `Controller.Evcs` kann daher grundsätzlich
nicht an eine `Evcs.Goe.Http`-Instanz binden, unabhängig von der
Konfiguration - siehe Analyse im Chatverlauf, bestätigt gegen den aktuellen
`develop`-Branch von github.com/OpenEMS/openems.

Laut OpenEMS-Community-Forum
(https://community.openems.io/t/go-e-gemini-wallbox-an-fenecon-home-10/10217)
ist das kein Versehen: es gab wiederholte Entwicklerberichte, dass ältere
go-e-Firmwareversionen nicht für dauerhaftes, hochfrequentes Beschreiben
ausgelegt waren, was zu Geräteausfällen führte - deshalb ist offizielle
Schreibunterstützung für Gemini bislang nicht in OpenEMS gelandet.

Dieses Bundle wurde bewusst als **separate, neue Komponente** gebaut (nicht
als Änderung an `io.openems.edge.evcs.goe`), um:

* die bestehende, produktiv laufende Nur-Lese-Installation unangetastet zu
  lassen (Downgrade-Pfad: einfach diese Komponente deaktivieren, die alte
  bleibt unverändert nutzbar),
* das Schreibverhalten bewusst gedrosselt zu implementieren (siehe unten),
  um das oben beschriebene Risiko zu adressieren, statt es zu ignorieren.

== Schreibdrosselung (Antwort auf das Firmware-Risiko)

Zwei voneinander unabhängige Schutzmechanismen:

* **Framework-seitig** (`AbstractManagedEvcsComponent`/`WriteHandler`,
  Standard-OpenEMS-Code, nicht Teil dieses Bundles): schreibt nur, wenn sich
  der angeforderte Sollwert um mehr als 50 W ändert, oder wenn seit dem
  letzten Schreiben `getWriteInterval()` Sekunden vergangen sind - kein
  Schreiben bei stabilem Sollwert.
* **Config-Feld `writeIntervalSeconds`** (Standard 30 s, hier überschreibt
  dieses Bundle den OpenEMS-Standardwert explizit statt sich nur auf den
  Default zu verlassen): steuert genau dieses Intervall. Bei Bedarf weiter
  erhöhen, falls weiterhin Bedenken wegen Geräteverschleiß bestehen.

== Nicht-blockierende Schreibzugriffe

Schreibbefehle (`/api/set?amp=...&frc=...`) werden über
`BridgeHttp#request()` **asynchron** (fire-and-forget mit Callback)
gesendet, nicht blockierend. Das adressiert ein zweites, im
OpenEMS-Community-Forum dokumentiertes historisches Problem bei
go-e-Integrationen: blockierende HTTP-Aufrufe im Cycle-Schreib-Handler
konnten frühere Implementierungen das gesamte OpenEMS zeitweise einfrieren
lassen. Erfolg/Fehlschlag eines Schreibvorgangs wird asynchron im
Diagnose-Channel `LastWriteFailed` sichtbar, nicht als Rückgabewert der
synchronen `applyChargePowerLimit()`/`pauseChargeProcess()`-Methoden (die
laut `ManagedEvcs`-Vertrag nur "wurde gesendet", nicht "wurde bestätigt",
zurückgeben müssen).

== Read-only-Schutzschalter (`readOnly`-Config-Feld)

Standardmäßig `true`: die Komponente liest Status/Messwerte ganz normal,
sendet aber **nie** Schreibbefehle - `WriteHandler` (Standard-OpenEMS-Code)
prüft vor jedem Schreibversuch `isReadOnly()` und bricht sonst ab. Damit
lässt sich die Komponente gefahrlos einrichten und beobachten (inkl.
`Controller.Evcs` im Scheduler), bevor sie tatsächlich steuert - erst nach
bewusstem Umschalten auf `false` sendet sie echte `amp`/`frc`-Befehle an die
Wallbox. Beeinflusst auch den gemeldeten `MeterType`
(`CONSUMPTION_METERED` vs. `MANAGED_CONSUMPTION_METERED`), analog zum
Original-Gemini-Bundle.

== API-Feld-Zuordnung (go-e API v2)

[cols="1,1,1"]
|===
|go-e-Feld |Bedeutung |Verwendung hier

|`car` |Ladezustand (0=Unknown/Error, 1=Idle, 2=Charging, 3=WaitCar, 4=Complete, 5=Error, 6=Initializing) |auf `Evcs.Status` abgebildet, Rohwert zusätzlich in `GoeCarState`
|`amp` |zuletzt vom Gerät bestätigter Ladestrom [A] |`CurrUser` [mA]
|`nrg` |Legacy-Energie-Array (Spannungen/Ströme/Leistung je Phase) |Spannungs-/Strom-/Leistungs-Channels von `ElectricityMeter`
|`err` |Fehlercode |`GoeError` (Rohwert)
|`alw` |geräteseitig aktuell freigegeben? |`AllowedToCharge`
|`fwv` |Firmware-Version |`FirmwareVersion`
|===

Schreiben: `amp=<A>` (Ladestrom) zusammen mit `frc=2` (force On) beim Laden;
`frc=1` (force Off) beim Pausieren. `frc=0` (Neutral, externe/App-Steuerung
entscheidet) wird von diesem Bundle nie gesetzt - sobald diese Komponente
aktiv ist, hat sie immer eine explizite Meinung (An oder Aus), nie "neutral".

== Kumulierte Energie und `EnergySession`

Die go-e API v2 liefert nur Momentanleistung (`nrg[11]`), keinen kumulierten
Energiezähler. Kumulierte Energie (`ElectricityMeter.ActiveProductionEnergy`
- das ist hier korrekt, nicht `ActiveConsumptionEnergy`, siehe unten) und
`EnergySession` (Energie seit Beginn der aktuellen Ladesitzung, in der
Live-Kachel/History als "Verbraucht"/"Energie seit Ladebeginn" sichtbar)
werden daher aus der Leistung integriert, genau wie im mitgelieferten
Nur-Lese-Bundle `Evcs.Goe.Http`:

* `CalculateEnergyFromPower` (Standard-OpenEMS-Utility) integriert
  `ActivePower` fortlaufend zu `ActiveProductionEnergy` auf, mit
  Timedata-gestütztem Warmstart (setzt beim Aktivieren mit dem letzten
  historisierten Wert fort, statt bei 0 neu anzufangen).
* `CalculateEnergySession` bildet daraus `EnergySession` = aktueller
  `ActiveProductionEnergy`-Wert minus dessen Wert beim letzten Wechsel
  "kein Fahrzeug verbunden" -> "Fahrzeug verbunden" (`car` wechselt von 1
  auf 2/3/4) - true "Energie seit Ladebeginn" der laufenden Sitzung.
* `ActiveProductionEnergy` (nicht `ActiveConsumptionEnergy`) ist hier
  richtig: beide Utilities integrieren/vergleichen konsistent das, was
  dieser Meter selbst als (immer positive) `ActivePower` meldet - identisch
  zum Vorgehen im Original-Bundle `Evcs.Goe.Http`. Wie diese Werte auf
  Systemebene (`_sum`) als Verbrauch verrechnet werden, ist unabhängig davon
  und Sache des Sum-Components, nicht dieses Bundles.
* Beide Berechnungen laufen im `TOPIC_CYCLE_AFTER_PROCESS_IMAGE`-Event, mit
  eigenem, dynamischem (optionalem) `Timedata`-Reference - ohne konfigurierten
  `Timedata`-Provider (z. B. `Timedata.Rrd4j`) bleiben die Werte einfach bei
  0/undefined (fail-safe, kein Fehler).

== Voraussetzungen

* go-e Gemini mit aktueller Firmware (API v2, `/api/status`/`/api/set`
  erreichbar - mit `curl http://<ip>/api/status` im Browser/Terminal
  testbar).
* Component-ID **muss sich von der bestehenden `Evcs.Goe.Http`-Instanz
  unterscheiden** (Standard hier: `evcs1`, falls die alte `evcs0` heißt) -
  beide können parallel existieren (eine liest nur, die andere steuert),
  aber nicht auf demselben Component-ID-Namen.
* Für PV-Überschussladen zusätzlich `Controller.Evcs` mit `Charge-Mode =
  Use surplus power` einrichten und im Scheduler eintragen (`Evcs-ID` muss
  auf die ID dieser neuen Komponente zeigen, nicht auf die alte
  Nur-Lese-Instanz).

== Phasenumschaltung (`psm`) - manuell und automatisch

Umschaltbar zwischen ein- und dreiphasigem Laden, per Klick in einer eigenen
Live-Kachel (nicht Teil der geteilten, generischen Evcs-Live-Kachel, siehe
unten) - wahlweise manuell erzwungen oder mit einer eigenen,
PV-Überschuss-basierten Automatik.

=== Warum kein eigener, generischer Controller

Ein naheliegender erster Gedanke war ein eigenständiger
`Controller.Ess`/`Controller.Evcs`-artiger Controller für die automatische
Umschaltung. Das würde aber faelschlich suggerieren, es gaebe dafuer eine
generische OpenEMS-Schnittstelle, die fuer beliebige Wallboxen gilt -
tatsaechlich unterstuetzt **keine** andere EVCS-Implementierung in diesem
Repo Phasenumschaltung ueberhaupt (kein entsprechender Kanal in
`io.openems.edge.evcs.api` oder einer der anderen `io.openems.edge.evcs.*`-Bundles).
Die Automatik-Logik lebt deshalb direkt in diesem, ohnehin schon
go-e-spezifischen Bundle statt in einem separaten, allgemein klingenden
Controller.

=== OpenEMS-seitiger Steuerungsmodus (`PhaseControlMode`)

Neuer Kanal `PhaseControlMode`/`SetPhaseControlMode` (`Automatic`/`Force
1-phase`/`Force 3-phase`) - **dieses Bundle ist die einzige Stelle, die
tatsaechlich `SetPhaseSwitchMode` (das rohe go-e-Feld `psm`) beschreibt**.
Die Live-Kachel schreibt seitdem nicht mehr direkt `SetPhaseSwitchMode`,
sondern `SetPhaseControlMode` - dadurch gibt es nie zwei unabhaengige
Schreiber, die sich gegenseitig ueberschreiben koennten.

`Automatic` bedeutet **nicht** das geraeteeigene `psm=0`. Stattdessen
entscheidet `evaluatePhaseControlMode()` jeden Cycle selbst, indem der
"natuerliche" PV-Ueberschuss (Netzleistung mit der eigenen aktuellen
Ladeleistung herausgerechnet, wie bei `Controller.Ess.ArbitrageDischarge`)
mit einem konfigurierten Schwellwert (`phaseSwitchThresholdWatt`, Default
5000 W) verglichen wird. Damit kurze Wolkenschatten nicht zu staendigem
Hin-und-Her-Schalten fuehren, muss die Bedingung eine konfigurierte Dauer
lang **durchgehend** gelten, bevor tatsaechlich umgeschaltet wird -
bewusst asymmetrisch: `phaseSwitchUpDurationSeconds` (Default 5 Minuten)
fuer den Wechsel auf 3-phasig, `phaseSwitchDownDurationSeconds` (Default 10
Minuten, laenger) fuer den Wechsel zurueck auf 1-phasig.

**Default ist `Force 1-phase`, nicht `Automatic`** - bei jeder (Re-)Aktivierung
der Komponente (auch nach einem Neustart), nicht nur beim allerersten Mal.
Automatische Umschaltung muss explizit ueber die Live-Kachel aktiviert
werden.

=== Lade-Prioritaet (`Controller.Evcs`) wird beim Ueberschuss beruecksichtigt

Ein einfaches "Netzleistung minus Wallbox-Eigenverbrauch" als Ueberschuss
reicht nicht: `Controller.Evcs` hat selbst eine `Priority`-Einstellung
(`Auto`/`Speicher`), die bestimmt, ob PV-Ueberschuss primaer ins EV oder in
den Speicher fliesst. Bei Speicher-Vorrang ist "eingespeiste Leistung" die
richtige Groesse; bei Auto-Vorrang wuerde das die tatsaechlich fuers EV
verfuegbare Leistung unterschaetzen, weil die Batterie-Ladeleistung dabei
nicht mitgezaehlt wird - genau das Symptom, das den ersten Testlauf dieser
Automatik ausgebremst hat (genug PV fuer 3-phasig, Prioritaet stand auf
Auto-Vorrang, trotzdem lief der groessere Teil in den Speicher).

`isCarPriority()` liest deshalb, welche Formel gilt - **nicht** ueber eine
zweite, separat zu pflegende Einstellung in diesem Bundle (Risiko: beide
Schalter laufen auseinander), sondern **live** von der tatsaechlichen
`Controller.Evcs`-Instanz (`Config#evcsControllerId()`, Default
`ctrlEvcs0`) via `ConfigurationAdmin` - generisch ueber
`OpenemsComponent#servicePid()` und `getConfiguration(pid, "?")
.getProperties().get("priority")`, keine Compile-Abhaengigkeit auf
`io.openems.edge.controller.evcs`. Es gibt dadurch nur eine einzige Quelle
der Wahrheit. Schlaegt das Lesen fehl (falsche/leere Component-ID,
Komponente nicht gefunden, o. ae.), wird sicherheitshalber wie bei
Speicher-Vorrang gerechnet (unterschaetzt den Ueberschuss im Zweifel,
statt ihn zu ueberschaetzen).

Die beiden Formeln entsprechen exakt `ControllerEvcsImpl`s eigenen
(`calculateChargePowerFromExcessPower`/`calculateExcessPowerAfterEss`),
nur ohne dessen 200-W-Puffer und ohne die dortige SOC>97%-Sonderregel
(vereinfachend bewusst weggelassen, siehe Chatverlauf).

**Falsches Feld korrigiert**: Frühere Version dieser readme.adoc nannte `psh`
als (fehlendes) Phasenumschaltungsfeld - das war ungenau. `psh` ist nur die
Hysterese-Einstellung [W] für die geräteeigene Automatik. Das eigentliche
Schreibfeld ist `psm` (`phaseSwitchMode`: 0=Automatisch, 1=Einphasig
erzwingen, 2=Dreiphasig erzwingen). `fsp` (`force_single_phase`) existiert
zwar auch, ist auf dieser Firmware aber **nur lesbar** - ein Schreibversuch
liefert vom Gerät selbst den Hinweis, stattdessen `psm` zu verwenden.

**Empirisch getestet** (nicht in der offiziellen go-e-API-v2-Doku
dokumentiert): Nach dem Schreiben von `psm` unterbricht die Gemini den
Ladevorgang kurz von sich aus (sichtbar am `modelStatus`-Wert `24` =
`NotChargingBecauseMinPauseDuration`) und setzt die Ladung danach
**selbstständig** wieder fort (`modelStatus` zurück auf `3` =
`ChargingBecauseForceStateOn`), ohne dass `frc`/`amp` erneut gesetzt werden
müssen. Die dafür nötige Wartezeit wird also **vom Gerät selbst** verwaltet
(vermutlich über die ebenfalls schreibbaren `mptwt`/`mpwst`/`psmd`-Felder
konfigurierbar) - dieses Bundle muss die Pause/Wartezeit daher **nicht**
selbst orchestrieren, sondern schreibt `psm` einmalig bei Klick und wartet
ansonsten nicht aktiv.

Channels: `SetPhaseSwitchMode` (WriteChannel, 0/1/2 - wird nur noch intern
von diesem Bundle selbst beschrieben), `PhaseSwitchMode` (vom Gerät zuletzt
bestätigter Wert), `ModelStatus` (Rohwert des go-e-Feldes `modelStatus` -
Diagnose, warum gerade (nicht) geladen wird, z. B. während des kurzen
Phasenwechsel-Unterbruchs), `PhaseControlMode`/`SetPhaseControlMode`
(OpenEMS-seitiger Steuerungsmodus, siehe oben - das ist der Kanal, den die
Live-Kachel tatsächlich beschreibt), `PhaseAutomaticLastDecision`
(String, nur im Modus `Automatic` gefüllt - zeigt Prioritäts-Formel,
Einspeisung/EV-Ladung/Speicher-Leistung, berechneten Überschuss,
Schwellwert und Hysterese-Status im Klartext; `null` in den beiden
Force-Modi).

**Eigene Live-Kachel statt der geteilten Evcs-Kachel**: Die normale
Live-Ansicht-Kachel für EVCS-Komponenten (`Controller_Evcs`) ist in OpenEMS
eine geteilte Komponente, die alle Evcs-Implementierungen gemeinsam nutzen
(matched über die `Evcs`-Nature, nicht die Factory-ID) - eine Änderung daran
würde alle EVCS-Typen betreffen. Der Umschalter sitzt daher in einer
eigenständigen, zusätzlichen Mini-Kachel
(`ui/.../edge/live/Controller/Evcs/GoeGeminiManaged/`), die nur erscheint,
wenn die konfigurierte Komponente die Factory-ID `Evcs.Goe.Gemini.Managed`
hat - der geteilte Code bleibt unangetastet.

== Bekannte Einschränkungen

* Kein Display-Text (`applyDisplayText` gibt immer `false` zurück - go-e
  Gemini hat über API v2 kein beschreibbares Display-Textfeld, anders als
  die ältere "Charger Home"-Baureihe).
* Firmware-/Legacy-Filter-Fallback (wie im Nur-Lese-Bundle für sehr alte
  Firmware < 51.4) wurde bewusst weggelassen - Gemini-Geräte sollten auf
  API-v2-fähiger Firmware laufen.
* Nicht offiziell von go-e oder FENECON unterstützt - eigenes Risiko, siehe
  Abschnitt oben zu Firmware-Berichten. Schreibintervall im Zweifel eher
  großzügig (höher) statt knapp konfigurieren.
