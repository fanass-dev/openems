= Fronius Batteriespeicher (ESS) via JSON/HTTP (Solar API v1 + Steuerung)

Implementiert ein `ManagedSymmetricEss` in OpenEMS für den Batteriespeicher
eines Fronius Hybrid-Wechselrichters (GEN24 oder Symo Hybrid) - **ohne
Modbus/SunSpec**:

* **Lesen** (immer aktiv, offiziell dokumentiert): SoC, Leistung, Kapazität,
  Zellgesundheit über die Fronius Solar API v1 (`GetStorageRealtimeData.cgi`).
* **Schreiben/Steuern** (optional, `ControlMode != READ_ONLY`, **inoffiziell
  und undokumentiert**): Lade-/Entladesteuerung über die Web-Config-API des
  GEN24-Webinterfaces (Digest-Auth über HTTP) - siehe eigener Abschnitt
  unten, unbedingt vor Produktivbetrieb lesen.

Endpunkt: `http://<inverter-ip>/solar_api/v1/GetStorageRealtimeData.cgi?Scope=Device&DeviceId=0`

Vorher im Browser testen:

  http://<inverter-ip>/solar_api/v1/GetStorageRealtimeData.cgi?Scope=Device&DeviceId=0

Verfügbarkeit laut Fronius: Hybrid-Geräte ab HybridManager 1.1.2-13, GEN24 ab
Firmware 1.13.

== Steuerung: Wozu, und warum "inoffiziell"?

Die offizielle, dokumentierte Fronius Solar API kann den Speicher nur
auslesen - kein Hersteller-Endpunkt zum Schreiben ist dokumentiert. Der
einzige bekannte Weg, den Speicher ohne Modbus/SunSpec (das auf dem GEN24
bekannte Bugs hat, siehe
https://community.openems.io/t/laden-entladen-am-fronius-symo-gen24-hybridwechselrichter-mit-modbus/1549)
aktiv zu steuern, ist die **inoffizielle, undokumentierte Web-Config-API**
des GEN24-Webinterfaces - dieselbe API, die auch die Fronius-eigene
Weboberfläche und Drittprojekte wie
https://github.com/muexxl/batcontrol[batcontrol] und
https://github.com/evcc-io/evcc[evcc] verwenden. Dieses Bundle bildet daher
**beide Rollen in einer Component** ab: `ManagedSymmetricEss` (statt nur
`SymmetricEss`), damit Standard-OpenEMS-Controller
(`Controller.Ess.Balancing`, `Controller.Ess.FixActivePower`,
`Controller.Ess.GridOptimizedCharge`, ...) diese Component ganz normal als
Sollwertgeber verwenden können.

[WARNING]
====
Diese Web-Config-API ist von Fronius nicht dokumentiert, nicht offiziell
unterstützt und kann sich mit jedem Firmware-Update ändern oder ganz
wegfallen (siehe die entsprechende Diskussion:
https://github.com/evcc-io/evcc/discussions/21472). Sie überschreibt außerdem
die eigene Zeit-/Energiemanagement-Logik des Wechselrichters. Anders als bei
den beiden reinen Lese-Bundles (Meter, PV-Inverter) schreibt dieses Bundle im
Steuerungsmodus **aktiv Befehle an ein laufendes Batteriesystem** - teste
das unbedingt zunächst vorsichtig (z. B. mit `Controller.Debug.Log` statt
einem echten Regel-Controller, kleine Leistungswerte, Beobachtung im
Fronius-Webinterface) bevor du es produktiv/automatisiert einsetzt.
Standardmäßig ist `ControlMode = READ_ONLY` gesetzt - **es wird nie etwas
geschrieben, bis du das explizit umstellst.**
====

== Warum ein separates Bundle statt "HybridEss"

Der GEN24 ist intern ein Hybrid-Gerät (PV + Speicher + Netzanschluss in
einem Gehäuse), OpenEMS kennt dafür die Nature `HybridEss` (kombinierte
AC-Leistung an einem gemeinsamen Netzanschlusspunkt, um Doppelzählung zu
vermeiden). Da du PV-Erzeugung und Netz/Zähler bereits über zwei eigene,
unabhängige Bundles abbildest
(`io.openems.edge.pvinverter.fronius.json` bzw.
`io.openems.edge.meter.fronius.smartmeter.json`), folgt dieses ESS-Bundle
demselben, einfacheren Standard-Modellierungsmuster: **drei unabhängige
Components** (Meter + PV-Inverter + Ess) für ein physisch kombiniertes
Gerät - genau wie es auch das offizielle OpenEMS-"Getting started"-Tutorial
mit Simulator-Komponenten vorschlägt.

== Flaches JSON (anders als beim PV-Wechselrichter!)

Mit `Scope=Device` liefert dieser Endpunkt - anders als
`GetInverterRealtimeData.cgi` - wieder **flache** Zahlen direkt unter
`Body.Data.Controller.<Feld>`, **nicht** verschachtelt in
`{Value, Unit}`-Objekte:

[source,json]
----
{
  "Body": {
    "Data": {
      "Controller": {
        "Details": { "Manufacturer": "BYD", "Model": "BYD Battery-Box Premium HV", "Serial": "..." },
        "Enable": 1,
        "StateOfCharge_Relative": 65.9,
        "Capacity_Maximum": 7800,
        "DesignedCapacity": 7800,
        "Current_DC": 0.8,
        "Voltage_DC": 321.3,
        "Temperature_Cell": 16.0,
        "Status_BatteryCell": 3,
        "TimeStamp": 1650606867
      },
      "Modules": []
    }
  }
}
----

Ist der angeschlossene Batterietyp von der Solar-API-Version nicht
unterstützt, liefert Fronius `"Body":{"Data":{}}` mit
`Head.Status.Code=255` - dieses Bundle erkennt das (fehlendes
`Controller`-Objekt) und setzt dann nur `SLAVE_COMMUNICATION_FAILED`,
statt einen Fehler zu werfen.

== Steuerungsmechanik im Detail

=== Authentifizierung: Digest-Auth mit Rolling Nonce

Die Web-Config-API verlangt HTTP Digest-Auth (nicht Basic-Auth):

1. Erste Anfrage ohne `Authorization`-Header -> Antwort `401` mit einem
   Nonce (`WWW-Authenticate`, teils auch nur `X-WWW-Authenticate`/
   `X-Www-Authenticate` - Schreibweise je Firmware unterschiedlich).
   Realm ist fest `"Webinterface area"`.
2. Client berechnet `HA1 = hash(user:realm:passwort)`,
   `HA2 = hash(methode:pfad)`,
   `response = hash(HA1:nonce:nc:cnonce:qop:HA2)` und sendet das im
   `Authorization: Digest ...`-Header (inkl. `qop=auth`, achtstelligem
   `nc`-Zähler, zufälligem `cnonce`).
3. Bei Erfolg liefert Fronius **erneut** einen (neuen) Nonce im selben,
   nicht-standardkonformen Header zurück, der für den nächsten
   Schreibvorgang verwendet werden muss ("Rolling Nonce") - `nonce`/
   `cnonce`/`nc` werden deshalb zwischen Aufrufen im Bundle zwischengespeichert
   (`FroniusControlClient`).

Hash-Algorithmus ist **firmwareabhängig**: MD5 unterhalb Firmware
`1.38.6-1`, SHA-256 ab `1.38.6-1`. Ebenso die Endpunkt-Pfade: unterhalb
Firmware `1.36` ohne `/api`-Prefix (`/config/batteries`, `/status/version`,
...), ab `1.36` mit (`/api/config/batteries`, `/api/status/version`, ...).
Das Bundle ermittelt beides automatisch beim ersten Schreibversuch über
`GET /api/status/version` (unauthentifiziert).

Diese ganze Handshake-Logik ist eine Java-Neuimplementierung des in Python
geschriebenen, quelloffenen https://github.com/muexxl/batcontrol[batcontrol]-
Projekts (`src/batcontrol/inverter/fronius.py`) - der einzigen bekannten
öffentlichen "Dokumentation" dieser API.

=== Zwei Steuerungsmodi (`controlMode`-Konfigurationsfeld)

[cols="1,2,2"]
|===
|Modus |Mechanik |Charakter des Sollwerts

|`READ_ONLY` (Standard) |Keine Schreibzugriffe. `applyPower()` tut nichts. |-
|`SCHEDULE_BASED` |Schreibt **einen** Time-of-Use-Eintrag über
`POST /api/config/timeofuse` (00:00-23:59, alle Wochentage) |**Ober-/
Untergrenze**, kein erzwungener Momentanwert
|`GRID_POWER_TARGET` |Schreibt `HYB_EM_POWER`/`HYB_EM_MODE=1` über
`POST /api/config/batteries` |**Exakter Netz-Sollwert am
Netzanschlusspunkt** (nicht Batterieleistung!)
|===

**`SCHEDULE_BASED` (empfohlen)** - `applyPower(activePower, _)` wird wie
folgt übersetzt (OpenEMS-Konvention: negativ = laden, positiv = entladen).
Sowohl Lade- als auch Entladeseite werden **ausschließlich** aus
`activePower` selbst abgeleitet - dem einen Wert, den der Solver für diesen
Cycle bereits aufgelöst hat:

* `activePower <= -50 W` (laden gewollt) -> `ScheduleType=CHARGE_MIN`,
  `Power=|activePower|`: erzwingt eine **Mindest**-Ladeleistung (notfalls aus
  dem Netz, wenn PV nicht reicht). `CHARGE_MAX` wird hier bewusst
  weggelassen - der Speicher darf weiterhin mehr laden, falls PV-Überschuss
  reicht ("kein erzwungener Momentanwert").
* `activePower >= 50 W` (entladen gewollt) -> `ScheduleType=DISCHARGE_MAX`,
  `Power=activePower`: setzt eine **Obergrenze** fuer die Entladeleistung -
  der Speicher entlaedt nur so viel, wie der Hausverbrauch tatsaechlich
  abruft, **nicht** garantiert exakt dieser Wert. Zusaetzlich `CHARGE_MAX 0`,
  um Laden waehrenddessen zu blockieren.
* Nahe Null -> `ScheduleType=DISCHARGE_MAX`, `Power=0` (Obergrenze, kein
  erzwungener Wert - blockiert Entladen nur, solange kein Bedarf da ist).
  Zusaetzlich `CHARGE_MAX 0`.

WICHTIG (`DISCHARGE_MIN` ausprobiert und wieder verworfen - Instabilitaet mit
Balancing): Eine Zwischenversion schrieb hier `ScheduleType=DISCHARGE_MIN`
(erzwungene Mindest-Entladeleistung, analog zu `CHARGE_MIN`) statt
`DISCHARGE_MAX`, um echtes Erzwingen des Entladens zu ermoeglichen (fuer
Controller wie `Controller.Ess.FixActivePower`/`Cycle` mit
`relationship=EQUALS`, die einen echten Zwang statt nur einer Obergrenze
wollen). `DISCHARGE_MIN` existiert wirklich (siehe unten, wie es entdeckt
wurde) und funktioniert fuer diese Controller auch korrekt.

**In Kombination mit `Controller.Ess.Balancing` fuehrte das auf einer echten
Anlage aber zu einem sich aufschaukelnden Lade-/Entlade-Oszillieren** (staendiger
Wechsel zwischen Netzladen und Netzeinspeisung, beobachtet bei PV=0). Root
Cause: Balancing ist eine **geschlossene Regelschleife**, die auf den
tatsaechlich resultierenden Netzfluss reagiert. Ueberschiesst eine erzwungene
Entlade-Untergrenze (Geraet entlaedt mehr als der Hausverbrauch gerade
braucht), speist der Ueberschuss ins Netz ein - das sieht Balancing im
naechsten Zyklus als Einspeisung und korrigiert gegenteilig (weniger
entladen, im Extremfall sogar Laden anfordern), was selbst wieder
ueberschiessen kann - eine sich selbst verstaerkende Schwingung zwischen zwei
rueckkoppelnden Systemen (Balancings Live-Regelung und dem erzwungenen
Schreiben), ohne daempfendes Element dazwischen. `CHARGE_MIN` (erzwungene
Lade-Untergrenze) hat dieses Problem NICHT: Ueberschiesst sie (mehr laden als
die Untergrenze, z. B. aus PV-Ueberschuss), passt das zu Balancings eigenem
Ziel (mehr PV-Ueberschuss speichern ist gut) statt es ihm entgegenzuwirken -
keine Gegenreaktion, keine Schwingung.

**Deshalb aktuell wieder `DISCHARGE_MAX`** (reine Obergrenze) fuer "entladen
gewollt" - auf Kosten der Praezision fuer `FixActivePower`/`Cycle` (kein
echter Zwang beim Entladen moeglich), aber stabil mit `Balancing`. Diese
Einschraenkung ist bewusst in Kauf genommen, dieselbe Art Kompromiss wie beim
Laden (`CHARGE_MAX` wird beim Laden-Zweig ebenfalls bewusst weggelassen,
siehe oben) - nur diesmal nicht nur aus Praezisionsgruenden, sondern aus
Stabilitaetsgruenden.

`DISCHARGE_MIN` selbst existiert nachweislich (per Firefox-Netzwerkanalyse
entdeckt: Feld "Min. Entladeleistung" im GEN24-Webinterface, `FroniusControlClient
.writeTimeOfUse()` akzeptiert beliebige `ScheduleType`-Strings und wuerde es
weiterhin unterstuetzen) - falls in Zukunft ein Anwendungsfall NUR mit
erzwingenden Controllern (`FixActivePower`/`Cycle`), OHNE gleichzeitig aktives
`Balancing`, benoetigt wird, waere `DISCHARGE_MIN` dafuer isoliert
unproblematisch. Eine allgemeine Verwendung (wie zuletzt versucht) ist aber
nicht sicher, solange nicht zwischen "weichem Ziel" (Balancing) und "hartem
Zwang" (`relationship=EQUALS`) unterschieden werden kann - der Solver liefert
am Ende nur eine einzige Zahl, ohne Herkunftsinformation, siehe auch die
fruehere Diskussion zu `activePower`-Rueckverfolgung weiter oben.

Alle Regeln eines Aufrufs werden in **einem** POST geschrieben (siehe
`FroniusControlClient.writeTimeOfUse(List<TimeOfUseRule>)`), da
`POST /api/config/timeofuse` die komplette Zeitsteuerung ersetzt statt
einzelne Eintraege zu mergen - mehrere getrennte Aufrufe wuerden sich sonst
gegenseitig ueberschreiben. Bestaetigt per Firefox-Netzwerkanalyse: das
GEN24-Webinterface selbst sendet bei zwei gleichzeitig konfigurierten Regeln
(z. B. `DISCHARGE_MAX` + `DISCHARGE_MIN`) exakt ein zweielementiges Array in
einem POST.

WICHTIG (Zuverlaessigkeit von Wertaenderungen - `writeTimeOfUseForced()`):
Beim Testen wurde beobachtet, dass eine reine Wertaenderung einer bereits
aktiven Regel (z. B. `DISCHARGE_MIN` von 500 auf 700 W) von Fronius mit
HTTP 200 und bestaetigtem `writeSuccess` beantwortet wurde, der neue Wert am
Geraet aber nicht ankam (auch nach hartem Reload des Webinterface). Die
Root Cause ist nicht abschliessend geklaert (nicht bei Fronius dokumentiert),
zwei Verdaechtige wurden trotzdem behoben:

* `sendAuthenticated()` fordert jetzt **vor jeder** authentifizierten Anfrage
  zwingend einen frischen Nonce an, statt den von der letzten Antwort
  "rollierend" mitgelieferten Nonce weiterzuverwenden - falls dieser
  Mechanismus bei bestimmten Firmware-Staenden aus dem Tritt geraet und zu
  einem Replay einer alten (zwischengespeicherten) Antwort fuehrt, waere das
  eine plausible Erklaerung fuer "Erfolg gemeldet, aber nicht angewendet".
* `writeTimeOfUseForced()` schreibt jede tatsaechliche Regeländerung jetzt
  immer als **Deaktivieren-dann-Reaktivieren** (zwei POSTs: erst dieselben
  Regeln mit `Active=false`, danach wie gewuenscht) statt eines einzelnen
  In-Place-Werteupdates - falls Fronius intern eine bereits aktive Regel bei
  reiner Wertaenderung ignoriert, sollte das erzwingen, dass sie neu
  uebernommen wird.

Beide Massnahmen sind unbestaetigte Workarounds fuer eine nicht dokumentierte
API - falls das Problem weiterhin auftritt, waere ein systematischerer Test
(Wert mehrfach hintereinander aendern, beobachten ob das Muster reproduzierbar
ist) der naechste Schritt.

WICHTIG: `POST /api/config/timeofuse` **ersetzt die komplette Zeitsteuerung**
des Geräts, nicht nur einen einzelnen Eintrag. Falls du vor der Aktivierung
dieses Bundles bereits eigene Time-of-Use-Regeln im Fronius-Webinterface
angelegt hattest, würden diese sonst beim ersten Schreibvorgang unwiederbringlich
gelöscht. Das Bundle sichert deshalb automatisch die zum Aktivierungszeitpunkt
bestehende Zeitsteuerung (siehe "Backup/Restore bestehender Zeitsteuerung"
unten), bevor es zum ersten Mal selbst schreibt.

**`GRID_POWER_TARGET` (nur für erfahrene Nutzer)** - `activePower` wird 1:1
als `HYB_EM_POWER` (manueller Modus, `HYB_EM_MODE=1`) geschrieben. **Wichtig:**
das ist ein Sollwert **am Netzanschlusspunkt der gesamten Anlage**
(PV + Speicher + Netz kombiniert), nicht die Batterieleistung selbst! Ein
Standard-Ess-Controller wie `Controller.Ess.Balancing` berechnet seinen
Sollwert aber als gewünschte **Batterieleistung** - in diesem Modus bekommt
der Wert also eine andere Bedeutung als vom Controller beabsichtigt. Diesen
Modus daher nur mit einem selbst geschriebenen, darauf abgestimmten
Controller verwenden, nicht mit den Standard-Ess-Controllern.

=== Sicherheitsmechanismen im Bundle

* **Entkoppelter Schreib-Thread**: `applyPower()` selbst speichert den
  Sollwert nur schnell/nicht-blockierend zwischen (Vorgabe des
  `ManagedSymmetricEss`-Interfaces); der eigentliche, langsame
  Digest-Auth-HTTP-Schreibvorgang läuft alle 5 Sekunden in einem separaten
  Hintergrund-Thread, nicht im OpenEMS-Cycle-Worker.
* **Totzone** (`writeDeadbandWatt`, Standard 100 W) und **Mindestabstand**
  (`minWriteIntervalSeconds`, Standard 15 s) verhindern, dass bei staendig
  leicht schwankendem Sollwert ständig neu geschrieben wird.
* **Schreib-Verifikation**: Fronius bestätigt jeden erfolgreichen Schreibwert
  explizit im `writeSuccess`-Array der Antwort - das Bundle prüft das und
  meldet einen Fehler (`ApplyPowerFailed`-Channel), falls ein Wert nicht
  bestätigt wurde, auch wenn die HTTP-Antwort `200` war.
* **Backup/Restore bestehender Zeitsteuerung** (nur `SCHEDULE_BASED`): beim
  ersten Schreibversuch nach der Aktivierung liest das Bundle per GET die zu
  diesem Zeitpunkt auf dem Gerät aktive Zeitsteuerung aus und sichert sie in
  einer lokalen Datei `fronius-ess-<Component-ID>-timeofuse-backup.json`
  (analog zu `backup_time_of_use()`/`restore_time_of_use_config()` in
  batcontrol) - aber nur, falls diese Datei nicht schon existiert (schützt
  vor einem Edge-Neustart mitten im Betrieb, der sonst die eigene, bereits
  aktive Regel fälschlich als "Original" sichern würde). Beim Deaktivieren
  der Component wird die gesicherte Zeitsteuerung automatisch wieder
  geschrieben und die Backup-Datei anschließend gelöscht. Schlägt das
  Sichern oder Wiederherstellen fehl, wird nichts überschrieben bzw. die
  Backup-Datei bewusst nicht gelöscht - eine Warnung im Log verweist dann
  auf die manuelle Prüfung im Fronius-Webinterface.
* **Automatik-Rücksetzung beim Beenden**: falls keine Zeitsteuerung
  wiederhergestellt wurde (kein Backup vorhanden oder Restore fehlgeschlagen),
  versucht das Bundle zusätzlich best-effort, die zuletzt geschriebene eigene
  Regel zu deaktivieren bzw. `HYB_EM_MODE` auf `0` (automatisch)
  zurückzusetzen - damit eine entfernte/gestoppte Component den Speicher
  nicht dauerhaft im manuellen Modus stehen lässt. Das ist best-effort (kein
  Retry) - im Zweifel im Fronius-Webinterface prüfen.
* **Backoff bei Fehlern**: jeder der drei Schreib-/Lesepfade (Time-of-Use-
  Schreiben, Time-of-Use-Backup, `HYB_EVU_CHARGEFROMGRID`) hat einen eigenen
  exponentiellen Backoff (Start 5 s, verdoppelt sich pro Fehlschlag, Deckel
  bei 5 min) statt bei jedem 5-Sekunden-Zyklus erneut anzufragen. Grund:
  Fronius' GEN24-Firmware sperrt Logins nach mehreren fehlgeschlagenen
  Versuchen offenbar vorübergehend komplett (auch für das normale
  Webinterface) - ungebremstes Retry-Verhalten würde eine solche Sperre nur
  auslösen bzw. verlängern, statt dem Gerät Zeit zur Erholung zu geben. Bei
  Erfolg wird der Backoff sofort wieder zurückgesetzt.
* Fehler werden über den bereits vorhandenen `ManagedSymmetricEss`-Channel
  `ApplyPowerFailed` gemeldet (kein neuer Channel nötig), zusätzlich über
  den Diagnose-Channel `LastControlAction` (Klartext, letzte gesendete
  Aktion bzw. letzter Fehler).

=== Pflicht-Kanäle für den Power-Solver (AllowedChargePower, AllowedDischargePower, MaxApparentPower)

Ohne diese drei Kanäle erzwingt der OpenEMS-Power-Solver für dieses Ess
IMMER einen Sollwert von 0 W - unabhängig davon, welcher Controller aktiv
ist oder was er anfordert. Das war die Ursache für das Symptom "Max
Entladeleistung: 0" im Webinterface, das auch nach Aktivieren des
Balancing-Controllers und echtem Netzbezug bestehen blieb.

**Root Cause** (verifiziert im OpenEMS-Quellcode, nicht geraten): Die
Methode `createGenericEssConstraints()` in
`io.openems.edge.ess.core.power.v1.data.ConstraintUtil` baut für JEDEN
`ManagedSymmetricEss` in JEDEM Solver-Zyklus zwei Constraints:

[source,java]
----
result.add(createSimpleConstraint(coefficients, ess.id() + ": Allowed Charge",
        ess.id(), ALL, ACTIVE, GREATER_OR_EQUALS,
        ess.getAllowedChargePower().orElse(0)));

result.add(createSimpleConstraint(coefficients, ess.id() + ": Allowed Discharge",
        ess.id(), ALL, ACTIVE, Relationship.LESS_OR_EQUALS,
        ess.getAllowedDischargePower().orElse(0)));
----

Wird der Kanal nie gesetzt, liefert `.orElse(0)` den Wert 0 - der Solver
bekommt dadurch gleichzeitig `ActivePower >= 0` UND `ActivePower <= 0` als
bindende Nebenbedingung, was den Sollwert rechnerisch auf exakt 0 W fixiert.
Das betrifft jeden Controller gleichermaßen, auch Balancing.

Die Fronius Solar API (`GetStorageRealtimeData.cgi`) liefert diese Werte
nicht - ihr `Controller`-Objekt enthält nur Ladezustand, Spannung, Strom,
Kapazität und Zelltemperaturen, aber keinerlei Leistungsgrenzwerte (siehe
https://manuals.plus/m/7d638f5b3435943ccd44d7c6121da568a516c9a4a5cccf36e278601c3a244339.pdf[Fronius
Solar API V1 Dokumentation]). Die Werte müssen daher aus dem Typenschild
bzw. Datenblatt von Wechselrichter und Batterie stammen und sind seit
dieser Version über drei neue, editierbare Config-Felder einstellbar -
NICHT im Code fest verdrahtet:

[cols="1,1,2"]
|===
|Config-Feld |Standardwert |Bedeutung

|`batteryMaxChargePowerWatt`
|11682 W
|Wird als `AllowedChargePower` gemeldet (intern automatisch negativ
gesetzt). Richtwert aus dem Fronius-Datenblatt "Symo GEN24 12.0 Plus SC",
Feld "Max. AC charging power, depending on connected battery".

|`batteryMaxDischargePowerWatt`
|12000 W
|Wird als `AllowedDischargePower` gemeldet. Richtwert aus dem
Fronius-Datenblatt, Feld "Max. output power (Pac max)".

|`maxApparentPowerVoltAmpere`
|12000 VA
|Wird als `MaxApparentPower` gemeldet. Ebenfalls aus dem
Fronius-Datenblatt, Feld "Max. output power".
|===

Quellen für die Standardwerte:
https://www.fronius.com/en/help-center/solar-energy/products/solar-inverters/gen24/symo-gen24-plus/fronius-symo-gen24-12-0-plus-sc[Fronius
Produktseite Symo GEN24 12.0 Plus SC],
https://solar-distribution.baywa-re.de/out/media/22-Symo_GEN24_SC_SE_Product_Documents_Datasheet_Fronius_Symo_GEN24_SC_12_kW_EN_EN-English.pdf[BayWa
r.e. Datenblatt PDF].

WICHTIG: Der Wert 11682 W ist eine generische Fronius-Angabe für die
maximale AC-Ladeleistung "je nach angeschlossener Batterie" - er wurde NICHT
speziell für eine BYD Battery-Box Premium HVM bestätigt gefunden. Für eine
BYD HVM 16.6 (6 Module, 16,56 kWh nutzbar, die dem angegebenen "16,4 kWh"
am nächsten kommende Standardkonfiguration) liegt die batterie-eigene
Strom-/Spannungsgrenze (50 A bei ca. 307 V nominal) sogar deutlich höher
(ca. 15 kW) - der Wechselrichter ist hier also die engere Grenze. Ein
Inverter-Hersteller-Datenblatt (SMA) nennt für andere Wechselrichter mit
BYD HVM 16.6 Ladeleistungen von 7,4-10 kW und Entladeleistungen von
8,7-10,6 kW
(https://files.sma.de/downloads/STPSE-Batteries-TI-en-13.pdf[SMA
STPSE-Batteries-TI PDF]) - diese Werte sind aber SMA-spezifisch und nicht
direkt auf die Fronius-GEN24-Kombination übertragbar. Die Standardwerte in
dieser Config sind daher als Startpunkt zu verstehen: unbedingt gegen das
eigene Typenschild bzw. das Fronius-Inbetriebnahmeprotokoll prüfen und bei
Abweichung über die Konfiguration anpassen.

HINWEIS zu einer OpenEMS-API-Eigenheit: Anders als `AllowedDischargePower`
und `MaxApparentPower` bietet das `ManagedSymmetricEss`-Interface fuer
`AllowedChargePower` KEINE `_setAllowedChargePower()`-Komfortmethode (verifiziert
im Quellcode von `io.openems.edge.ess.api.ManagedSymmetricEss`) - das Bundle setzt
diesen Kanal daher direkt ueber `getAllowedChargePowerChannel().setNextValue(...)`.

Da diese Werte statische Eigenschaften der Hardware sind (keine
Live-Telemetrie), setzt das Bundle sie einmalig in `activate()` - laut
OpenEMS-Kanalimplementierung (`AbstractReadChannel.nextProcessImage()`)
behält ein Kanal seinen zuletzt gesetzten Wert unverändert bei, bis er
erneut explizit gesetzt wird; ein wiederholtes Setzen pro Zyklus ist daher
nicht nötig. Nach einer Änderung der drei Felder ist ein Neustart der
Component bzw. von Edge erforderlich (kein `@Modified`-Hot-Reload
implementiert).

=== Kein "ist ein Controller aktiv?"-Guard (bewusst entfernt)

Eine Zwischenversion hatte hier einen Schutzmechanismus: `applyPower()`
pruefte vor jeder Verarbeitung die drei eigenen Write-Kanaele
`SetActivePowerEquals`, `SetActivePowerGreaterOrEquals` und
`SetActivePowerLessOrEquals` mittels `getNextWriteValueAndReset()` - waren
alle drei in einem Zyklus leer, wurde der Schreibvorgang uebersprungen
("kein Controller aktiv, der vom Solver gelieferte Default-Wert 0 W soll
nicht als echter Steuerbefehl missverstanden werden").

**Warum das verworfen wurde:** Dieser Guard erkannte nur Controller, die wie
`Controller.Ess.Balancing` ueber `ess.setActivePowerEqualsWithFilter()` (bzw.
die analogen `-GreaterOrEquals`/`-LessOrEquals`-Methoden) gehen - diese
Komfortmethoden schreiben die drei genannten Channels. Etliche andere,
ebenso valide Controller (`Controller.Ess.FixActivePower`,
`Controller.Symmetric.LimitActivePower`, `Controller.Ess.Peakshaving`, u. a.)
rufen stattdessen `PowerConstraint.apply()`/`ess.addPowerConstraint()` DIREKT
auf - das geht am Solver vorbei zwar korrekt in die Constraint-Berechnung
ein (verifiziert per `ess0/DebugSetActivePower`), beruehrt aber keinen der
drei Write-Channels. Der Guard hielt das faelschlich fuer "kein Controller
aktiv" und verwarf den Schreibvorgang komplett - `ess0/LastControlAction`
blieb leer, obwohl der Solver den Sollwert korrekt aufgeloest hatte. Mit nur
`Controller.Ess.FixActivePower` (ohne zusaetzliches `Balancing`) liess sich
das gezielt reproduzieren.

**Kein Ersatz-Mechanismus noetig:** Es gibt keine zuverlaessige, generische
Moeglichkeit herauszufinden "hat irgendein Controller diesen Cycle wirklich
etwas fuer dieses Ess vorgegeben" - der Solver liefert am Ende nur eine
einzige Zahl, ohne Herkunftsinformation. Das eigentliche Risiko, vor dem der
Guard schuetzen sollte (`DISCHARGE_MAX 0` dauerhaft, weil noch kein
Controller lief), ist zudem kein echter Schaden: Ohne jeden verwaltenden
Controller ist "vorsichtshalber nicht laden/entladen" ein vernuenftiger,
sicherer Default. Das tatsaechlich kritische Szenario - eine *bereits
bestehende* Zeitsteuerung des Nutzers beim allerersten Schreibvorgang nicht
versehentlich zu ueberschreiben - ist ohnehin durch einen unabhaengigen
Mechanismus abgedeckt: `backupTimeOfUseConfig()` sichert die
Ausgangs-Zeitsteuerung, bevor ueberhaupt zum ersten Mal geschrieben wird.
`applyPower()` verarbeitet den vom Solver gelieferten Wert daher jetzt
immer, ganz ohne Sonderfall - so wie es z. B. auch
`EssFeneconCommercial40`/`AbstractGenericManagedEss` (die eingebauten
Referenz-Ess-Implementierungen) tun, die applyPower() ebenfalls ungeprueft
ausfuehren (bei denen ist ein "0 W ohne Controller"-Wert allerdings
folgenlos, da dort ein Echtzeit-Register jede Sekunde neu geschrieben wird -
anders als unsere persistente Zeitsteuerungs-Regel, die nur alle ~15 s
geschrieben wird, siehe naechster Abschnitt zur Traegheit).

=== Saisonale Nutzung mit Standard-OpenEMS-Controllern

`ManagedSymmetricEss` sagt nichts über die *Absicht* hinter einem
Sollwert aus - `applyPower()` bekommt immer nur eine einzige, bereits von
der OpenEMS-Power-Engine aufgelöste Watt-Zahl, unabhängig davon, welcher
Controller sie letztlich verursacht hat. Zwei fertige Standard-Controller
decken genau das eingangs beschriebene Szenario ab, haben aber
gegensätzliche Erwartungen an eine Lade-Anforderung:

[cols="1,2,1"]
|===
|Jahreszeit |Controller |Erwartung an CHARGE_MIN

|Frühjahr-Herbst |`Controller.Ess.GridOptimizedCharge` (verzögert Ladung
anhand PV-/Verbrauchsprognose bis zu einer Zielzeit, z. B. 17:00 Uhr;
erzwingt bei Bedarf früheres Laden nur um Einspeisebegrenzung/Abregelung zu
vermeiden) |Reine **Kappung** des PV-Überschusses - **nie** aus dem Netz
nachladen
|Winter |`Controller.Ess.Time-Of-Use-Tariff`, Modus `CHARGE_CONSUMPTION`
(plant anhand Day-Ahead-Preisen einen 24h-Fahrplan in 15-Minuten-Schritten,
lädt gezielt in günstigen Preisfenstern) |**Erzwungener** Zielwert, darf
auch aus dem Netz kommen (z. B. nachts ohne PV)
|===

Damit `CHARGE_MIN` in beiden Fällen das Richtige tut, gibt es das
Konfigurationsfeld `allowGridCharging`, das unabhängig vom Sollwert selbst
das Fronius-Flag `HYB_EVU_CHARGEFROMGRID` setzt:

* `allowGridCharging = false` (Standard, für Frühjahr-Herbst mit
  `GridOptimizedCharge`): `CHARGE_MIN` wirkt real nur als Kappung - reicht
  der PV-Überschuss kurzfristig nicht, wird trotzdem **nicht** aus dem Netz
  nachgezogen.
* `allowGridCharging = true` (für den Winter mit `Time-Of-Use-Tariff` /
  `CHARGE_CONSUMPTION`): `CHARGE_MIN` darf den Sollwert auch durch
  Netzbezug erfüllen.

Aktuell **manuell** umschalten (z. B. zwei openEMS-Konfigurationen für
Controller + `allowGridCharging`, die du im Frühjahr/Herbst tauschst). Eine
automatische, jahreszeit- oder KI-basierte Umschaltung ist bewusst noch
nicht umgesetzt - möglicher späterer Ausbauschritt, sobald der manuelle
Betrieb sich bewährt hat.

Das Flag wird beim Start der Steuerung einmalig geschrieben (nicht bei
jedem Schreibvorgang) und bei einem fehlgeschlagenen Versuch automatisch im
nächsten Kontrollzyklus wiederholt.

Nicht gesetzt (von diesem Endpunkt nicht geliefert):

* `GRID_MODE` - die Solar API liefert an dieser Stelle keine
  Netz-Status-Information; der Channel bleibt `UNDEFINED` (Standardwert).
* `REACTIVE_POWER` - keine Blindleistungsdaten in `GetStorageRealtimeData.cgi`.
* `ALLOWED_CHARGE_POWER`, `ALLOWED_DISCHARGE_POWER`, `MAX_APPARENT_POWER` -
  von der Solar API ebenfalls nicht geliefert, werden seit dieser Version
  aber einmalig aus den Config-Feldern `batteryMaxChargePowerWatt` /
  `batteryMaxDischargePowerWatt` / `maxApparentPowerVoltAmpere` gesetzt -
  siehe "Pflicht-Kanaele fuer den Power-Solver" oben. Ohne diese Werte
  wuerde der OpenEMS-Power-Solver den Sollwert immer auf 0 W zwingen.
* `ACTIVE_CHARGE_ENERGY` / `ACTIVE_DISCHARGE_ENERGY` - dieser Endpunkt liefert
  keine kumulierten Lade-/Entlade-Energiezähler; falls du diese Werte
  brauchst, mit `CalculateEnergyFromPower` aus `ACTIVE_POWER` selbst
  integrieren (Standard-OpenEMS-Baustein).

== Wichtig: Vorzeichen und AC- vs. DC-Leistung

Fronius dokumentiert `Current_DC` explizit als "battery output current
(+ charging)" - also **positiv beim Laden**. OpenEMS erwartet bei
`SymmetricEss.ACTIVE_POWER` das Gegenteil: **negativ beim Laden, positiv
beim Entladen**. Das Bundle rechnet deshalb:

  ACTIVE_POWER = -(Voltage_DC * Current_DC)

Das ist die **DC-Leistung an den Batterieklemmen**, nicht die AC-Leistung
am Netzanschlusspunkt - Wandlerverluste (i. d. R. wenige Prozent) sind hier
nicht enthalten. Für reine Beobachtung (SoC-Verlauf, Lade-/Entladezyklen in
Grafana) ist das mehr als ausreichend genau.

== Lade-/Entladeenergie (`ActiveChargeEnergy`/`ActiveDischargeEnergy`)

**Wichtig, falls Beladung/Entladung in der History-Ansicht 0 kWh anzeigen:**
Anders als z. B. bei `ElectricityMeter` (dessen `ActiveProductionEnergy`/
`ActiveConsumptionEnergy` automatisch aus `ActivePower` integriert werden)
sind `SymmetricEss.ACTIVE_CHARGE_ENERGY` und `ACTIVE_DISCHARGE_ENERGY` reine
Channels ohne automatische Berechnung - jede Ess-Implementierung muss sie
selbst befüllen (siehe z. B. das eingebaute `Ess.Samsung`-Bundle als
Vorlage). Dieses Bundle tut das über `CalculateEnergyFromPower`, aufgerufen
bei jedem `ACTIVE_POWER`-Update mit der oben beschriebenen
OpenEMS-Vorzeichenkonvention (negativ = Laden, positiv = Entladen). Dafür
wird optional eine `Timedata`-Referenz (typischerweise `Timedata.Rrd4j`)
gebunden, damit die kumulierten Wh-Werte einen Neustart des Edge überleben,
statt bei jedem Neustart wieder bei 0 zu beginnen.

Gleiches Prinzip wie bei den anderen beiden Bundles: `pollEveryCycles`

== Einbau ins Projekt

1. Diesen kompletten Ordner `io.openems.edge.ess.fronius.json/` direkt
   neben die anderen Edge-Bundles legen.
2. In `io.openems.edge.application/EdgeApp.bndrun` das Bundle wieder an
   zwei Stellen alphabetisch eintragen:
+
[source]
----
# im -runrequires Block:
bnd.identity;id='io.openems.edge.ess.fronius.json',\

# im -runbundles Block:
io.openems.edge.ess.fronius.json;version=snapshot,\
----
+
Danach "Resolve" und "Update" in der `EdgeApp.bndrun`-Ansicht ausführen.
3. Bundle bauen (in Eclipse importieren wie bei den beiden vorherigen
   Bundles, oder `./gradlew :io.openems.edge.ess.fronius.json:build`).
4. In der Edge-Config eine Component-Instanz vom Typ `Ess.Fronius.Json`
   anlegen: Component-ID z. B. `ess0`, IP `192.168.188.10` (dein GEN24),
   Device-ID `0`. `controlMode` zunächst auf `READ_ONLY` (Standard)
   belassen, um erst einmal nur zu beobachten.
5. Damit hast du für Anlage 1 (GEN24) nun drei zusammengehörige,
   unabhängige Components: `meter0` (Netz/Smart Meter), `pvInverter1`
   (PV-Erzeugung) und `ess0` (Batteriespeicher) - z. B. nutzbar in einem
   eigenen Energiefluss-Widget oder zur reinen Beobachtung/Protokollierung
   in InfluxDB/Grafana.
6. **Erst wenn das läuft:** Steuerung optional aktivieren - `controlMode`
   auf `SCHEDULE_BASED` (empfohlen) oder `GRID_POWER_TARGET` umstellen,
   `username` (Standard `customer`) und `password` deines
   GEN24-Webinterface-Zugangs eintragen. Erst danach kann `ess0` als
   Sollwertgeber in einem Ess-Controller (`Controller.Ess.Balancing`,
   `Controller.Ess.FixActivePower`, ...) verwendet werden.

== Bekannte Einschränkungen

* Nur Fronius-eigene Hybrid-Geräte (GEN24, Symo Hybrid) unterstützen diesen
  Endpunkt überhaupt - ein reiner (nicht-hybrider) Symo ohne Speicher
  liefert hier grundsätzlich keine Daten (`NOT AVAILABLE` laut
  Fronius-Doku) - für deine Anlage 2 (Symo ohne Speicher) ist dieses Bundle
  also nicht relevant/nicht nutzbar, was zu deiner Beschreibung passt.
* Manche Felder (`Temperature_Cell_Minimum/_Maximum`, `Status_BatteryCell`)
  sind laut Fronius-Doku je nach Batterietyp/Firmware nicht immer
  vorhanden - die entsprechenden Channels bleiben dann einfach
  `undefined`, das ist kein Fehler dieser Implementierung.
* `Modules[]` (Detaildaten je Batteriemodul, z. B. Zellspannungen pro
  Modul) wird aktuell nicht ausgelesen - bei Bedarf nach demselben Muster
  ergänzbar.
* Steuerung ist **inoffiziell/undokumentiert** (siehe oben) - kann sich mit
  Firmware-Updates ändern; Standardeinstellung ist deshalb `READ_ONLY`.
* `SCHEDULE_BASED` liefert Obergrenzen (`CHARGE_MAX`/`DISCHARGE_MAX`) bzw.
  einen erzwungenen Mindestwert nur beim Laden (`CHARGE_MIN`), aber nie einen
  exakten Momentanwert im Sinne von "genau X W, nicht mehr und nicht
  weniger" - insbesondere Entladen kann NICHT erzwungen werden
  (`DISCHARGE_MIN` existiert zwar, ist aber wegen Instabilitaet mit
  `Controller.Ess.Balancing` bewusst nicht im Einsatz, siehe oben);
  `GRID_POWER_TARGET` interpretiert den Sollwert als Netz- statt
  Batterieleistung - beides ist eine Näherung an das, was ein
  Standard-Ess-Controller eigentlich erwartet (siehe Abschnitt "Zwei
  Steuerungsmodi").
* Keine Blindleistungssteuerung möglich - `reactivePower` in
  `applyPower()` wird ignoriert.
* Reaktionszeit der Steuerung ist durch den 5-Sekunden-Hintergrund-Thread
  plus Totzone/Mindestabstand begrenzt - kein Echtzeitregelkreis, eher für
  langsame Optimierungs-Controller (z. B. Preis-/PV-Prognose-basiert)
  geeignet als für schnelle Netzdienstleistungen.
